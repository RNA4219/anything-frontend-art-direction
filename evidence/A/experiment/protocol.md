# Paired forward execution protocol — A

- Campaign: `anything-frontend-design-engineering-A-20261123`
- Base: `f5df625dbc577d6a3ca28e13ef09e39b135b4a6f`
- Date: 2026-11-23 (Asia/Tokyo)
- Two public development cases: operational support triage / course discovery and comparison.
- The cases are development fixtures, **not a private holdout**.
- Both executions receive identical brief bytes, the same neutral output contract, fixed visual intent and the same inherited model. Model sampling settings, billed token cost and runtime image digest are not exposed by this harness; record them as unknown.
- Baseline receives the pinned root Art Direction Skill and its reference files. Candidate receives those same files plus `extensions/A/SKILL.md` and its method references.
- Use fresh agent threads with no parent history for both arms. Do not pass expected findings, oracle results or the other arm's output. Permit reads only of each arm's input directory, and writes only to its output directory. Shared-filesystem logical separation is documented; it is not OS-enforced isolation.
- Same deliverable: one design plan JSON per case. Preserve requirement IDs, content and visual intent. No access to checks, test assertions, comparison result, other arm, R-ASI policy or reviewer files during generation.
- Generation does not run tests or revise after seeing the evaluator. Any later revision is a new attempt, with old outputs retained.
- Apply a common deterministic HTML projection to both plans, with identical content, CSS and viewer behavior. This tests the structural proposal; it does not attribute renderer behavior to the Skill.
- Run contract/invariant checks and browser navigation inspections on both outputs. Distinguish function, information architecture, interaction, visual and implementation findings.
- A fresh reviewer receives anonymized plan files, public briefs and the neutral contract only, after both outputs are frozen. Hide arm labels and source paths. This is a model review with concealed labels, not a human user study or a separately hosted oracle.
- Count issues by evidence-backed invariant, not by preferences. Record screens and navigation edges descriptively, never assume fewer screens/choices is better.
- Promotion stays provisional unless independent evaluation requirements are satisfied. No observed difference is a valid result; do not manufacture a weak baseline or claim measured human completion rates.

## Common generation request

Use the supplied Skill material to design Product Design / Information Architecture for the two supplied briefs. Decide which requested functions to retain, merge, defer or remove; account for mandatory requirements and role boundaries; design screen responsibilities and navigation. Preserve the supplied content and visual intent. Write one JSON plan per case using the supplied contract. Work from the brief; mark assumptions and unresolved questions. Do not implement state transitions or redesign appearance. Do not browse outside the supplied input directory, run evaluators, or read tests/other outputs. Report the paths and any uncertainty.

The only treatment difference is the additional Product Design / IA Skill file and references in the candidate input directory. Raw requests, inputs, outputs, model limitations and hashes are retained.
