## 予約の判断

### 入力と送信意図を分けた

名前は前後の空白を除いて検証し、空白だけでは受け付けない。人数文字列は数値へ変換して1〜8の整数か確認する。空欄、空白、0、9、小数、数値でない文字列はAPIを呼ばず入力エラーにする。入力途中の無効値もdraftに保持する。

有効な送信を始める時点で、正規化済み入力と操作識別子を固定する。送信応答待ちと結果不明の間は、入力の変更や破棄を受け付けない。連打は同じ進行中の操作を増やさず現在のsnapshotを返す。

### 確定失敗と結果不明を区別した

APIが確定失敗を返した場合は入力を残し、同じ操作識別子で再試行できる。利用者が入力を編集してから送る場合には新しい識別子を割り当てる。

結果不明になった送信は、後の再試行が確定失敗しても最初の送信結果が不明であることを保持する。照会で見つからない場合も未実行とは決めつけず、同じ操作識別子で再試行する。照会中は照会・再試行を重ねない。

成功はAPIが返したreceiptに基づき、予約番号・名前・人数を表示する。成功後の`submit()`は何もしない。「別の予約を入力する」操作で新しい編集を明示的に始める。

### 破棄とserver上の予約を混同しない

未送信の入力、または未確定の予約が存在しない確定失敗だけを破棄できる。送信中・結果不明の画面では、閉じても予約の取消しにならない説明を表示する。このAPIには予約取消し操作がないため、画面上にも予約を取り消したという表示は作らない。

## 在庫取込みの判断

### 最後に確認したserverの結果を保持する

開始の応答待ちは「開始を受け付けています」、serverが処理を返してからは「取込みを処理しています」と表示する。項目の結果と進捗はjobから描画する。3件すべての処理が終わっていても、失敗項目があれば一部失敗の表示にする。

`poll()`の待機中は表示済みのjobを保持する。読取り失敗でも、すでに取得した成功項目や進捗を消さない。更新は明示的な`poll()`だけで行い、controllerに自動ポーリングや自動再試行は入れていない。

### 失敗項目だけを再試行する

`job.results`のfailed項目だけから再試行対象を作る。応答待ち中の連打を抑止し、応答不明の場合は同じ再試行識別子と対象を保持する。成功した項目は再処理しない。再試行でfailedがpendingへ戻るとprocessed件数もserverの値に合わせて減少する。

### 取消しと古い応答を整理する

取消し要求から応答までをcancellingとし、serverが返したjobの結果で確定する。要求後に全件成功していた場合には成功を表示する。

同じjobではversionが小さい応答を採用しない。成功済み・取消済みのjobをrunningへ戻さない。さらに、取消し・再試行より前に始まったpollは操作世代で区別し、その後の表示を上書きさせない。別のjobへの復帰や新しい選択では文脈を更新するため、以前のjobのversionや遅い応答と混同しない。

### 復帰は読取りで行う

`resume(jobId)`はloadingから`getJob`を呼び、返されたid/nameに選択内容を合わせる。存在しないjobIdならfailedと説明を返す。controllerの復帰は新しいjobを作らない。

通常デモでは共通fixtureがメモリ上のため、別モジュールが通常操作の記録を端末内に保存し、再読み込み時にfixtureを復元する。その後、新しいcontrollerが保持したjobIdを`resume()`で読み戻す。保存が使えない場合は、画面を閉じる前に結果を確認する案内を表示する。この保存・再生はデモのためのもので、実serverの永続化ではない。

## 画面・文言・操作追加の責務

固定のインク色`#172323`、紙色`#f6f2e9`、アクセント`#245b48`を使った。見出しは`"Yu Mincho", "Hiragino Mincho ProN", serif`、本文と操作は`system-ui, sans-serif`で、外部font読込みはない。

広幅は2領域を横並びにし、760px以下では同じDOM順序のまま縦に並べる。gridの列は`minmax(0,1fr)`、入力幅は領域内の100%、操作群は折り返しとし、固定の横幅を設けていない。結果の長い文字列も領域内で折り返す。

以下の文字量の増加は、操作結果と修復手段を説明するための追加である。

- 予約の結果不明で「予約結果を確認する」「同じ予約を再試行する」と、画面を閉じても取消しにならない説明を追加した。
- 取込みに処理済み件数、成功・失敗・中止の件数、各項目の文字による結果を追加した。
- 取込みには進捗更新、失敗項目だけの再試行、中止の要求と応答待ち、前の取込みを読み戻す操作を用意した。
- 初期画面で不要な回復操作は表示せず、前の取込みの照会欄はdetails内に置いた。
- エラーは色だけに頼らず文言と対象欄を結び付けた。状態変化は持続する文字で表示し、アニメーションは追加していない。

内部phase名、request key、API呼出し回数、テスト結果、故障操作は製品UIに表示しない。表示する「予約番号」と「処理番号」は、利用者が結果を見直すためのreceipt/jobの番号である。

| 結果不明後の確定失敗 | 最初の結果不明を保持し、その後の照会で既存receiptを取得した。 |

| 中止要求と全件成功の競合 | serverが成功を返した場合はsucceededになった。 |
| pollの失敗、成功後の古い応答 | 既知の項目結果を保持し、成功済みを処理中へ戻さなかった。 |
| 既存jobへの復帰、存在しないjob、別jobのversion | 復帰で書込みを増やさず、項目内容を復元した。別jobのversionとは比較しなかった。 |
| 取込み開始・失敗項目再試行・取消しの結果不明 | 同じ操作で再送、またはpollで結果を確認した。 |
| snapshotとsetItemsの独立性 | 呼出し側が返却値や元配列を書き換えても内部状態は変わらなかった。 |
| デモ保存・復元 | メモリ上の保存代替を使い、別fixtureへ同じjob・進捗・項目結果・version・generationを復元した。 |
| HTMLの静的条件 | 指定文言、色、書体、共通APIへの相対import、狭幅CSS、status領域と説明関連付けを確認した。 |

## 未検証事項・限界

- ブラウザー操作は指定により試していない。1280px・390pxの実描画、実フォント、折返し、横スクロール、Tab/Enterの実操作、フォーカス移動、支援技術での読み上げは未検証である。静的コード検査を画面確認の成功として扱っていない。
- デモの保存・復元は代替storageを用いてNodeで検証した。実ブラウザーのlocalStorage・ページ再読込み・pagehideは未検証である。
- 端末内保存は単一画面の通常デモ用である。複数タブでの保存競合や、実サービスの認証・永続化・トランザクションは保証していない。
- 同一識別子による重複抑止は共通APIの契約を前提としている。実serverが同じ契約を提供するかは別途確認が必要である。
- 外部資料、他条件の出力、共通評価用ファイル、指定外の資料は参照していない。比較点数や優劣の自己採点はしていない。
