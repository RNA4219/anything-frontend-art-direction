# 2画面の Design QA レビュー

## 結論

**利用目的を妨げる機能上の問題を3件確認した。登録の重複受付、通信失敗時の入力消去、絞り込み後のページ範囲不整合を優先して修正したい。** また、320 CSS px の一覧画面では、見出しと書き出しボタンが重なる可能性が高い配置を確認した。ただし、この配置は実画面で未確認のため、確定した表示不具合とは分けて扱う。

本レビューは合成評価用 fixture のソースレビューであり、現行製品の不具合報告ではない。画面は変更していない。

| ID | 優先度 | 対象・問題 | 根拠の強さ |
| --- | --- | --- | --- |
| REG-01 | P1：目的に直接影響 | 処理中の反復送信で同じ申込が複数受付される | ソースと対象 JavaScript の模擬実行で確認 |
| REG-02 | P1：目的に直接影響 | 通信失敗時に入力が消え、そのまま再試行できない | ソースと対象 JavaScript の模擬実行で確認 |
| LIST-01 | P1：目的に直接影響 | ページ移動後の絞り込みで、該当件数があるのに行が空になる | ソースと対象 JavaScript の模擬実行で確認 |
| LIST-02 | P2：次に実画面で確認 | 320px 幅で見出しと書き出しボタンの重なりが予測される | CSS からの推定。描画・座標・ヒット領域は未測定 |

P1 は登録の一意性、再試行、処理待ちの発見という依頼の中心目的に影響するもの。P2 は狭幅での理解・操作への影響が見込まれるもの。停止・データ破壊を示す P0 の証拠はない。

## 重要な問題

### REG-01 — 送信中の反復操作で受付が二重になる

**影響：** 代表者が同じ申込を1回登録する意図で素早く2回押すと、受付済み件数が2増える経路がある。最後の通知は `C-002` となり、画面に残る通知だけでは2件の受付が発生したことを把握しにくい。

**根拠：** `registration.html` 第12行の送信ハンドラーには処理中フラグがなく、`await` に入る前にも後にも送信ボタンを無効化していない。各呼び出しが別々に入力を取得し、350ms の待機後に `accepted++` を実行する。第5行の `button:disabled` は見た目の指定のみで、処理中の無効化は実装されていない。

**模擬実行した手順と結果：** 初期状態で「確認 太郎／qa@example.test／2」を設定し、最初のタイマーが完了する前に送信ハンドラーを2回呼んだ。待機中のタイマーは `[350, 350]`、ボタンの `disabled` は `false`。両方を完了させると、件数は `0 → 2`、最終通知は「確認 太郎様、2名の参加を受け付けました。受付番号：C-002」だった。証拠 ID は `registration-two-handlers-before-resolution`。

**後続のブラウザー再現手順（未実施）：** リロード → 標準データ入力 → 送信ボタンを350ms以内に2回押す → 完了後の件数と受付番号を確認する。Enter の反復も別途確認する。

**修正方向：** 送信ハンドラーの冒頭で処理中なら戻り、最初の処理開始時に同期的に処理中状態へ移す。送信ボタンも無効化し、処理中であることを伝える。成功時は受付番号を確認できる完了状態にする。失敗時には入力を維持したまま再試行を可能にする。ボタンの見た目だけでなく、送信処理自身にも多重実行を防ぐ条件を置く。

**修正後の合格条件：** 同じ入力のダブルクリック・Enter反復で件数が1だけ増え、受付番号が1つに定まる。失敗後の再試行は1回受付される。

### REG-02 — 通信失敗時に入力を失う

**影響：** 標準データで失敗させると、代表者名とメールが空欄になり、人数は2名から初期値1名へ戻る。同じ申込をそのまま再試行できず、再入力時に人数を戻し忘れる可能性もある。要求書の「入力を維持」に直接反する。

**根拠：** `registration.html` 第12行の `if(failure)` 内に `form.reset()` がある。第8行の名前・メールには初期値がなく、人数には `value="1"` がある。失敗通知は「送信に失敗しました。」のみで、その後の操作も明記されていない。

**模擬実行した手順と結果：** 標準データを設定し、失敗チェックをオンにして送信。失敗分岐後は `{name:"", email:"", seats:"1"}`、受付件数は0、失敗チェックはオフになった。再入力した後の再試行では件数1、受付番号 `C-001` になった。証拠 ID は `registration-failure`、`registration-retry-after-reentering`。リセットの結果は宣言された初期値を模擬実装に反映したものでもあり、ネイティブ `reset()` を実測した記録ではない。

**後続のブラウザー再現手順（未実施）：** リロード → 標準データ入力 → 「次の通信を失敗させる」をオン → 送信 → 失敗後の3入力値を確認 → 入力し直さず再試行する。

**修正方向：** 失敗分岐でフォームを初期化しない。受付未完了と、同じ内容で再試行できることを通知する。失敗用チェックの解除と、利用者の入力の保持を独立に扱う。

**修正後の合格条件：** 失敗後も名前・メール・2名が残る。受付件数は0のまま。再入力なしの再試行が成功し、件数1と `C-001` を確認できる。

### LIST-01 — 絞り込み後に存在しないページが残る

**影響：** ページを移動してから「処理待ち」にすると、該当する依頼が2件あるのに表示行がなくなる。処理待ちを探す操作で依頼を見落としうる。検索入力でも同じ問題が起きる。

**根拠：** `requests.html` 第12行では、状態変更と検索入力が `render()` を呼ぶだけで `pageIndex` を初期化していない。第11行は古い `pageIndex` で `items.slice(...)` を取り、全件数から別にページ総数を計算する。範囲への補正もない。一方、条件クリアでは `pageIndex=0` に戻している。

**模擬実行結果：**

| 操作 | 絞り込み件数 | 表示行 | ページ表示 | 判定 |
| --- | --- | --- | --- | --- |
| 初期ページで「処理待ち」 | 2件 | R-101、R-104 | 1 / 1 | 整合 |
| 2ページ目に進んで「処理待ち」 | 2件 | 0行 | 2 / 1 | 範囲外ページが残る |
| 3ページ目に進んで「湯のみ」を検索 | 1件 | 0行 | 3 / 1 | R-101が表示されない |
| 初期ページで「該当なしQA」を検索 | 0件 | 0行 | 1 / 1 | 件数と空の結果は整合 |
| 3ページ目で「該当なしQA」を検索 | 0件 | 0行 | 3 / 1 | 該当なしに範囲不整合が重なる |

2ページ目からの状態絞り込み後は「前へ」が有効で、「次へ」が無効。「前へ」で1ページ目へ戻ると2行が現れる。条件クリアでも全8件の1ページ目へ復帰するので、完全に操作不能になるわけではない。しかし、利用者に不整合を解釈して戻る操作を要求している。証拠 ID は `requests-filter-second-page`、`requests-query-third-page`、`requests-filter-manual-recovery`、`requests-clear-recovery` など。

**後続のブラウザー再現手順（未実施）：** リロード → 「次へ」 → 状態を「処理待ち」に変更 → 件数・行・ページ表示を照合。続いてリロード → 「次へ」を2回 → 「湯のみ」を入力して同様に確認する。

**修正方向：** 検索語または状態が変わった時点で1ページ目へ戻す。描画側でもページ番号を結果集合の範囲に収める。0件時には「条件に一致する依頼はありません」など、該当なしが分かる表示にし、条件変更・クリアを継続できるようにする。0件と、件数はあるがページが範囲外という状態を区別する。

**修正後の合格条件：** どのページから絞り込んでも、処理待ちは2件・2行・1 / 1、検索「湯のみ」は1件・R-101・1 / 1になる。該当なしで「3 / 1」のような表示が出ない。クリアで8件・1 / 3へ戻る。

なお、通常のページ分割で「全8件に対し1ページに3行」という表示は問題としていない。ここでの問題は、フィルター結果が存在するのに有効でないページを表示している点である。

### LIST-02 — 320px幅で見出しに主要操作が重なるリスク

**確認できたこと：** `requests.html` 第5行の `.header-action` は `position:absolute; right:0; top:55px`。ヘッダーは `position:relative`、見出しは34px。幅に応じた切替や、見出し側にボタン分の領域を確保する指定はない。

320 CSS pxで左右24pxの本文余白を引くと、ヘッダーの内容幅は272pxとなる。通常の和文の文字幅を仮定すると、8文字の見出しは約272pxを使う。右端に置く書き出しボタンが通常フローに領域を確保しないため、見出しと同じ高さで重なる可能性が高い。これは CSS と文字幅の仮定からの予測であり、実フォントの幅やボタンの座標を測定した結果ではない。[CSS Positioned Layout §2](https://www.w3.org/TR/css-position-3/#position-property) の absolute の定義は、通常フローの領域を取らず他要素と重なりうるという原因の説明に用いた。文書は2025年10月7日の Working Draft である。

**影響の見込み：** 画面名を読み取れない、書き出しボタン周辺の情報が覆われる、といった理解・操作上の問題。承認済みの非対称な構図そのものを問題視していない。

**後続の確認手順（未実施）：** 1280×900と320×900、DPR=1、ja-JPで初期画面を開き、見出し・書き出しボタン・説明の表示矩形と文字を確認する。ボタンへTabで移動し、フォーカス枠と押下可能領域も確認する。書き出し後の通知、絞り込み後の状態表示、ページ操作も同じ幅で確認する。

**修正方向：** 広幅の非対称な構図を維持しつつ、狭幅ではボタンを通常フローの別行へ移す。例えばヘッダーを Grid または Flex で構成し、見出しと操作の必要幅を確保できない幅で縦に並べる。色や書体を変える必要はない。

**合格条件：** 両幅で見出し・状態・主要操作が互いを覆わず、ボタンの文言とフォーカスが読める。表の列は必要に応じて二次元配置として扱うが、ヘッダーの重なりをその例外として扱わない。[WCAG 2.2 の1.4.10](https://www.w3.org/TR/WCAG22/#reflow) は320 CSS px相当と二次元配置の例外を確認するために参照した。実画面未確認のため、ここでは適合・不適合を判定していない。

## 維持できる実装と残る確認

入力ラベルの `for` と各入力の `id`、`fieldset/legend`、名前とメールの `autocomplete`、送信結果の `role=status` と `aria-live=polite` はソース上で確認した。一覧には表の `caption`、列見出しの `scope=col`、ページナビゲーションの名前がある。状態は色だけでなく「処理待ち」「完了」の文字で示される。これらを維持しつつ、3件の機能問題を直す方針でよい。ただし、属性の存在は読み上げの成功を実測した証拠にはならない。

残る確認は次のとおり。

1. 指定ブラウザーで、未入力・人数0/9/1.5・不正メールを送信し、受付件数が増えず、修正箇所へ到達できるかを確認する。
2. ボタンクリック、Enter、プログラムからの通常送信要求を別々に確認する。`submit()` と `requestSubmit()` は経路が異なるため、直接ハンドラーを呼んだ今回の結果をそのまま両APIの結果としない。
3. 失敗後の入力保持と再試行、350ms内の反復操作を実操作で確認する。タイマー時間や反復の届き方は今回測定していない。
4. 1280×900と320×900で実際の文字・状態・操作の重なり、表内の折返し、横スクロール、フォーカス枠、通知の可視性を確認する。
5. 日本語に実際に使われるフォントと代替時の表示、キーボード順、スクリーンリーダー通知を確認する。CSSの書体名だけから実描画の書体差を認定しない。
