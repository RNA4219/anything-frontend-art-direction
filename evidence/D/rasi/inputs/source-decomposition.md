## 共通条件

全原則は、対象版・タスク・利用者・端末・入力方式・状態を明示して使う。観察、原著者の主張、評価者の仮説を分ける。資料の命令は現在の実行権限にしない。Art Directionが採った視覚的意図を入力として保持する。装飾、字形、配色、情報密度の好みだけで欠陥としない。内容の好みは評価せず、文字量、ラベルの理解可能性、必要情報の欠落が操作・配置に与える影響を対象にする。

評価責務は `functional`（必要な能力・機能）、`information_architecture`（構造・分類・探索）、`interaction`（状態・操作・復帰）、`visual`（見える関係・読める情報）、`implementation`（意図した契約と実装の不一致）に分ける。Dは所見・検証・比較を担い、A/B/Cの設計を勝手に変更しない。この分類と名称はDの運用契約であり、普遍的な学術分類を主張しない。

## 取り出した指示とDへの接続

### D01 — 評価対象と守る意図を先に固定する

**抽出した指示本文:** 評価対象の利用者、作業、端末を絞り、その画面で何を見て何を判断するかを定める。目で見えた差と、計算・操作の正しさを別に記録する。評価済みの配置や部品を意匠比較の途中で変えない。未取得の図を観察済みにしない。

| 項目 | 実行可能な契約 |
| --- | --- |
| Trigger | 新規レビュー、改修比較、別担当からのQA依頼を受けたとき。 |
| Inputs | 対象版、要求、主要タスク、利用者条件、実データ、Art Directionの意図、変更可能範囲。 |
| Decision Rules | 視覚的選択を欠陥とするには、要求、読解、操作、または明示した設計意図との不一致を示す。仕様不明は不具合の確定と区別する。 |
| Procedure | 対象と除外範囲を書き、要求ID・タスクID・保持すべき意図を紐付ける。評価後の記憶から基準を作り直さない。 |
| Output Contract | D追加: scope manifest（artifact ID/hash、要求、タスク、環境、意図、対象外、未確認）。 |
| Failure Modes | 見た目だけから機能を推定する。好みを視覚欠陥にする。A/B/Cの設計決定をDが書き換える。 |
| Verification | 各所見から該当タスクと要求または意図に戻れること。未知の項目を埋めたふりにしないこと。 |
| Sources | [C3-07/08](../../references/c-usability.md#c3-07)、[意匠の採用条件](../../references/visual-direction.md#visual-acceptance)、[visual-craft冒頭](../../references/visual-craft.md)。 |

制約・例外: 小修正は対象部分の評価でよい。対象外の画面を未検証として残すことは許されるが、サイト全体の合格には広げない。依存: Aの要求・タスク、Bの期待状態、Cの実装契約があれば入力する。欠けた場合も再現可能な所見は記録できる。信頼度: 既存指示からの抽出は高、manifestの具体項目は今回の実装上の推論。

### D02 — 印象を原子的な所見へ変換する

**抽出した指示本文:** 問題の再現条件を決め、操作で観察できた結果と根拠を記録する。具体的にどの状態でどの場所が変わり、何が読めるようになるかを示す。観察したことと予測したことを分ける。

| 項目 | 実行可能な契約 |
| --- | --- |
| Trigger | 「違和感」「分かりにくい」などの批評、ツールの警告、観察した不一致があるとき。 |
| Inputs | 画面/要素/状態、期待、実際、再現操作、証拠、根拠、影響を受けるタスク。 |
| Decision Rules | 位置・症状・根拠・影響・修正方向・再現手順が揃うまで確定所見にしない。「AI Slop」「ダサい」は欠陥根拠として使用しない。 |
| Procedure | 一つの原因候補と検証可能な症状に分ける。主責務を一つ定め、横断影響は別欄に置く。所見に対する反証例を試し、誤検出と未確認を残す。 |
| Output Contract | D追加: finding ID、責務、位置、症状、期待/実際、根拠、タスク影響、修正方向、再現、証拠ID、確度、状態。 |
| Failure Modes | 一件に複数原因を混ぜる。修正案を観察事実にする。一般論で任意のUIを不合格にする。 |
| Verification | 所見だけを渡した別の評価者が、同じ版・状態で同じ症状を再現できるかを確認する。 |
| Sources | [SKILLレビュー手順](../../SKILL.md#レビューでの使い方)、[C4-15/17/28](../../references/c-usability.md#c4-15)、[visual-direction制作メモ](../../references/visual-direction.md)。 |

制約・例外: スクリーンショットだけで観察可能な欠けや重なりは記録できるが、クリック後の挙動は未確認とする。依存: 問題の直し方は該当A/B/CまたはArt Directionへ渡す。信頼度: 再現した症状と原因仮説を別々に示す。単なる欄の充足は真偽の保証ではない。

### D03 — ヒューリスティックと規範を混同せず適用する

**抽出した指示本文:** 設計を確認する視点を先に選び、対象と条件を確かめる。経験則と適合判定に使う仕様は区別する。原則から外れた箇所は変更時の制約と合わせて判断し、例外の妥当性を利用者の観察で確かめる。

| 項目 | 実行可能な契約 |
| --- | --- |
| Trigger | 目視レビュー、既知heuristicによる点検、標準適合に関する所見を作るとき。 |
| Inputs | 根拠の種類、対象と例外、仕様の版、観察証拠、タスク影響。 |
| Decision Rules | normative requirement / author guidance / empirical finding / inferenceを分離する。一般的な経験則違反をWCAG違反とは呼ばない。研究値は対象・比較・分母を保つ。 |
| Procedure | 適用条件を照合し、基準・例外・観察を並べる。影響、再発/持続、回避可能性を記録し、根拠なしのseverityを付けない。 |
| Output Contract | D追加: criterion ID、適用理由、例外判定、出典の節、severity理由、追加確認条件。 |
| Failure Modes | ガイドを一律の義務にする。静止画で規格適合を断言する。評価者差を隠す。 |
| Verification | 仕様文の対象・例外に戻れること。主張の強さが出典を上回らないこと。 |
| Sources | [C-01](../../references/c-usability.md#c-01)、[C3-01/02/09/11](../../references/c-usability.md#c3-01)、[C6-25/26/34](../../references/c-usability.md#c6-25)、[HCI研究の利用条件](../../references/k-studies.md)。 |

制約・例外: source-indexで原典未確認となった資料は、既存索引の記述の存在だけを確認した状態である。Dの具体的なseverity段階はセッション内の運用基準として定義し、出典の段階と異なる場合は一致させたふりをしない。依存: Cの規格適合要件。信頼度: 原典照合の状態で決め、リンクがあるだけでは高信頼にしない。

### D04 — タスクを終端条件で測る

**抽出した指示本文:** 想定タスクを行動単位まで分け、初見の人が目標と操作を結び付けられるか、正しい操作の結果が分かるかを確かめる。画面の情報量、移動回数、経路の見つけやすさは別々に評価する。

| 項目 | 実行可能な契約 |
| --- | --- |
| Trigger | 目的の完了、操作回数、行き止まりや循環を評価するとき。 |
| Inputs | 開始状態、具体的な目的状態、利用者知識、許可された経路、完了oracle、入力方法。 |
| Decision Rules | ボタンのクリックや成功文言だけで業務完了としない。実際の状態・結果と完了条件を照合する。クリック数の減少だけで改善としない。 |
| Procedure | 開始から終端まで操作を順に記録し、各段階の期待・観察・分岐・戻り・追加操作を対応付ける。操作単位を比較前に固定する。 |
| Output Contract | D追加: task trace、完了/未完了/判定不能、操作数・再試行数・逸脱、終端証拠。 |
| Failure Modes | 模擬バックエンドの成功を実保存と書く。静止画から完了率を推定する。比較間で操作単位や分母を変える。 |
| Verification | 同じ入力・状態でtraceを再生し、業務終端または模擬終端を確認する。分母と未完了件を保持する。 |
| Sources | [C4-03/04/05/14](../../references/c-usability.md#c4-03)、[K3-13/14](../../references/k-studies.md#k3-13)、[K1-13](../../references/k-studies.md#k1-13)。 |

制約・例外: 自動ブラウザの時間は人間の所要時間ではない。人を対象とする成功率は人数・試行・支援条件が必要。依存: Aの目的とBのフロー。信頼度: 実行traceは対象ケースの観察、学習容易性や一般利用者への効果は未実験なら仮説。

### D05 — 失敗後の復帰を別の完了条件として確かめる

**抽出した指示本文:** 不正値で送信が止まること、直す欄が分かることを確認する。送信失敗後は入力とエラーの出る時点を比べる。楽観的更新は失敗させ、最後に保存できた状態へ戻ることを確かめる。中断・連打で古い状態が残らないか調べる。

| 項目 | 実行可能な契約 |
| --- | --- |
| Trigger | 入力、保存、非同期処理、取消しや再試行があるタスク。 |
| Inputs | 正常ケース、失敗注入条件、境界値、期待復帰状態、再試行手段。 |
| Decision Rules | エラー表示の存在と復帰可能性は別に判定する。失敗前の入力・保存状態・操作可能性を比較する。危険な二重実行がないかを見る。 |
| Procedure | 正常・異常・境界を最低一つずつ実行し、初期 → pending → success/error → retry/cancelの到達状態を記録する。 |
| Output Contract | D追加: 状態coverage、失敗注入条件、保持/喪失した情報、復帰trace、再試行結果、未実行の分岐。 |
| Failure Modes | 成功ケースだけで全体合格にする。入力欄が見えているだけで入力保持とする。エラーから再試行しない。 |
| Verification | 同一失敗を再現し、復帰後の値と状態を期待契約に照合する。 |
| Sources | [フォームchecklist](../../checklists/forms.md)、[モーションchecklist](../../checklists/motion.md)、[form例](../../templates/form.html)、[optimistic例](../../templates/optimistic.html)、[C2-07/08/10/11](../../references/c-usability.md#c2-07)。 |

制約・例外: 既存optimistic例の保存はページ内の250ms模擬処理で、ネットワーク/サーバー耐障害性の検証ではない。依存: B/Cの状態・値の契約。Dは同じ検査を記録可能にし、既存テンプレートを本番用へ書き換えない。

### D06 — 視覚階層・整列・密度をタスクとの関係で点検する

**抽出した指示本文:** 実内容を入れ、比較したい項目が同時に残るか、ラベルと値・商品と価格・エラーと対象欄の対応が保たれるかを確かめる。狭幅で必要情報や操作が欠ける場合は見直す。図から受ける印象と実測した効果は分ける。

| 項目 | 実行可能な契約 |
| --- | --- |
| Trigger | 読みづらさ、主操作の埋没、まとまりの誤認、狭幅崩れ、長文による重なりが疑われるとき。 |
| Inputs | 対象タスク、Art Directionの意図、実文量、viewport、状態、関連する情報組。 |
| Decision Rules | 均等間隔や整列を全画面へ強制しない。意図的な段違いと、対応関係を壊す配置を区別する。密度の善悪を空白面積だけで決めない。 |
| Procedure | 見出し・値・主操作の位置を指定し、関連組の距離、欠け、遮蔽、折返し、順序を実寸で確認する。幅・文量・状態を変え、観察可能な影響を記録する。 |
| Output Contract | D追加: 視覚所見のelement/region、viewport、症状、比較画像ID、タスクへの影響、仮説の限界。 |
| Failure Modes | 強調、装飾、非対称を自動的に欠陥にする。スクリーンショットから視線計測や購買改善を主張する。 |
| Verification | 対象画面の同じ条件で位置・欠け・対応関係を再確認し、必要なら意図を保つ局所比較を依頼する。 |
| Sources | [visual-acceptance](../../references/visual-direction.md#visual-acceptance)、[発見と比較・操作で密度を変える](../../references/visual-composition.md#発見と比較操作で密度を変える)、[広幅から狭幅へ組み直す](../../references/visual-composition.md#広幅から狭幅へ組み直す)、[visual-craft仕上げ](../../references/visual-craft.md#仕上げの判断)。 |

制約・例外: 長い本文の意味・題材の好き嫌いは対象外。ラベルの理解や重要情報不足はIA/interactionへ主責務を割り当てる。依存: Art Directionの意図、Aの情報優先順位、Cの実装。信頼度: pixel測定は観察された幾何、認知影響は実利用者の観察がなければ仮説。

### D07 — ブラウザと画像の証拠条件を保持する

**抽出した指示本文:** 実画面で広幅・狭幅と状態変化を確認する。実機、端末エミュレーション、PCブラウザの幅変更を区別する。フォントの読込み後、実描画と代替表示を確かめ、CSS指定だけで実描画を判断しない。キーボードで主要操作を最後まで試す。

| 項目 | 実行可能な契約 |
| --- | --- |
| Trigger | スクリーンショットを根拠にする、ブラウザで再現する、before/afterを撮影するとき。 |
| Inputs | browser/version、viewport、device scale、入力方式、font状態、data/clock、対象版、状態到達手順。 |
| Decision Rules | 静止画像はその瞬間の視覚証拠。操作・読み上げ・実機touchの検証を代替しない。初期表示と処理後を混ぜない。 |
| Procedure | 既知状態に戻し、必要なフォント/画像/非同期完了を確認する。決めた操作を行い、該当状態とtraceを保存する。遮蔽や非表示のため未観察の要素を除外する。 |
| Output Contract | D追加: capture manifest、画像/traceのhash、状態、実行方法、未確認の入力/支援技術。 |
| Failure Modes | ファイル名だけで版を識別する。別OSの文字差をデザイン欠陥にする。エミュレーションを実機と呼ぶ。 |
| Verification | 同じmanifestを使った再取得で、説明した状態と証拠が対応することを確かめる。 |
| Sources | [visual-composition冒頭](../../references/visual-composition.md)、[和文と欧文を合わせる](../../references/visual-craft.md#和文と欧文を合わせる)、[accessibility checklist](../../checklists/accessibility.md)。 |

制約・例外: pixelsを完全一致させる条件やmaskの具体的実装は新規追加であり、原典とブラウザ実装を別途確認する。動的領域をmaskする場合、検証対象そのものを隠さない。依存: ブラウザと対象アプリ。環境未提供での未実行は「失敗ゼロ」ではない。

### D08 — 比較で変えた要素と測定対象を一致させる

**抽出した指示本文:** 同じ目的・文言・データ・幅・状態で案を比べる。全体方向の比較を色だけの局所差で代用せず、小修正は対象部分に限定してよい。複数の要素を同時変更した結果を、一つの要素の効果に帰属しない。

| 項目 | 実行可能な契約 |
| --- | --- |
| Trigger | baseline/candidate、修正前後、Skillの追加効果を比較するとき。 |
| Inputs | 両成果物、要件・内容hash、環境、モデル/設定/試行条件、評価単位、差分。 |
| Decision Rules | D Skillの効果は評価の完全性・再現性・検出/誤検出で測れる。同じUIを両条件で評価して、UI自体のタスク成功が改善したとは言わない。 |
| Procedure | 変更因子を固定し、両条件の出力を同じrubricで測る。順序・再試行・失敗を記録し、差が他の条件に起因しないか調べる。 |
| Output Contract | D追加: paired manifest、同一条件/相違条件、観測値、差分、試行履歴、主張できる範囲。 |
| Failure Modes | candidateだけ要件や内容が増える。生成モデルが違うのにSkillの効果とする。都合のよい試行だけ残す。 |
| Verification | hash/設定/要求と比較単位の一致を検査し、非同等条件があれば暫定扱いにする。 |
| Sources | [visual-acceptance](../../references/visual-direction.md#visual-acceptance)、[K14-03/04/05/06](../../references/k-studies.md#k14-03)、[K14-07/23/25](../../references/k-studies.md#k14-07)。 |

制約・例外: 生成設定にアクセスできない場合は「一致を確認できない」と記録する。温度やseedを推測しない。依存: 固定したbaseline指示とcandidate指示。信頼度: 観察した差とSkillによる因果効果を分離する。

### D09 — LLMの批評を再現と反証に接続する

**抽出した指示本文:** 自動評価の指摘は実際に操作し、対象とツールの範囲を記録する。検出できたことと原因・修正案が正しいことを区別する。評価者は他者の所見を見る前に観察し、統合時に重複と妥当性を判定する。

| 項目 | 実行可能な契約 |
| --- | --- |
| Trigger | LLMが所見を出す、複数評価者の結果を統合する、blind評価を実施するとき。 |
| Inputs | 生の対象artifact、タスク、固定rubric、評価者ID、アクセス範囲、モデル/設定、未公開oracleの所在。 |
| Decision Rules | 自己採点を独立評価と呼ばない。別agentでも同じ期待解・診断を渡したらblindとは呼ばない。独立していても同一モデルの共通誤りは残り得る。 |
| Procedure | 所見を候補として受け取り、操作/仕様/反例で照合する。初期結果を独立に固定してから統合し、候補が見たデータと評価者が見たデータを記録する。 |
| Output Contract | D追加: evaluator manifest、access/contamination申告、所見判定、重複対応、未解決の不一致。 |
| Failure Modes | 回答例や意図した修正を配って評価する。未公開holdoutをCandidateへ渡す。LLMの自信を証拠にする。 |
| Verification | 作成者/評価者と入力の由来を追い、候補がoracleを読めなかったことを実装上の境界で確かめる。共有ファイルの名目的分離は隔離と主張しない。 |
| Sources | [C3-05/06/10](../../references/c-usability.md#c3-05)、[C5-26/28/32/37](../../references/c-usability.md#c5-26)、[K13-16/19/21/23](../../references/k-studies.md#k13-16)、[accessibility checklist](../../checklists/accessibility.md)。 |

制約・例外: このCampaignで厳密な隔離が成立しない場合、外部oracle・正式なblind評価の完了とは言わない。Dが同じagentによる予備試験をすること自体は可だがラベルを分ける。依存: 独立実行器とアクセス制御は別途必要。信頼度: 検出率の分母が既知欠陥集合でも、全欠陥を代表するとは限らない。

### D10 — 証拠の揃った範囲でゲートを判定する

**抽出した指示本文:** 優劣を見分けられないときは保留にし、足りない比較を行う。利用者への効果は実際に試した証拠がない限り仮説として残す。設計パターンが実際に役立った証拠を蓄積する。

| 項目 | 実行可能な契約 |
| --- | --- |
| Trigger | リリース/統合/昇格、回帰検査、過去の修正済み所見を再確認するとき。 |
| Inputs | 固定した受入条件、今回のartifact hash、検証結果、既知所見と状態、証拠参照、独立評価の状態。 |
| Decision Rules | D追加: 必須証拠の欠落はHOLD。確定した重大な未解決違反はREJECT。条件・検証・独立性を満たした範囲だけREADY FOR INTEGRATION。未実行や壊れた証拠をPASSに変換しない。 |
| Procedure | 所見をcurrent hashで再検証し、修正済み/再発/未再現/未確認を分ける。必要ケースと実行ケースを突き合わせ、receiptとhashを保存する。 |
| Output Contract | D追加: gate decision、適用対象、理由、未達条件、今回の検証resultと証拠、次に必要な最小作業。 |
| Failure Modes | 過去のissueを現行の未修正不具合と扱う。既知のチェックが通れば全体PASSとする。自作CASをR-ASI実行と呼ぶ。 |
| Verification | データ欠落、未知status、hash不一致、重大finding、独立性不足を入れたnegative fixtureで判定を確認する。 |
| Sources | [visual-acceptance](../../references/visual-direction.md#visual-acceptance)、[visual-craft仕上げ](../../references/visual-craft.md#仕上げの判断)、[K15-04/08/09](../../references/k-studies.md#k15-04)、今回ユーザーの最終受入条件。 |

制約・例外: gate名称・証拠schema・CAS・receipt連携は今回の実装要求であり、既存Art Directionに実装済みとしない。R-ASIのexecute/evaluate/promoteが未接続なら外部試験の実績だけを記録する。独立評価なしの肯定判定は暫定であり、正式PASSにしない。依存: R-ASIの実在するCLI/契約と別実行器。
