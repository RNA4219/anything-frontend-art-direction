# Q/R Design QAレビューの裁定

## 結論

**既知3ケースの検出、修正に必要な6要素、不確実性の扱いはQ/Rで同等。Rには、一次責務とownerの明示、証拠の版管理、対象品質とSkill昇格の判定分離という記録上の利点がある。** この1組から、Rの方法が一般に不具合を多く検出する、利用者の成功率を改善する、またはSkillを正式昇格させられるとは結論できない。総合点による勝者は設定しない。

| 比較軸 | Q | R | 裁定 |
| --- | --- | --- | --- |
| 既知ケース検出 | 3 / 3 | 3 / 3 | 同等。3件だけを分母とする。 |
| actionability | 18 / 18要素 | 18 / 18要素 | 同等。位置・症状・根拠・影響・修正方向・再現の存在を確認。 |
| 証拠外を観察済みと断定した対象所見 | 0件 | 0件 | この資料内で特定できた件数。全記述の真実性保証ではない。 |
| 一次責務・owner | 機能問題という説明はあるが、所見ごとの一次責務・owner指定なし | 既知3件すべてimplementation / C。視覚仮説はvisual / C | Rの引き渡し情報が明示的。 |
| artifact binding | 対象HTML2件のpath/hash、結果ログ、ランタイムあり | 対象・brief・主要入力・harness・log・構造化報告のpath/hashと照合記録あり | Rの結び付けが広い。今回、元artifact全体の再検証はしていない。 |
| 実ブラウザとの区別 | 模擬実行、未実施の実操作を明示 | 同じ区別に加えblocked、completion=null等を構造化 | 核心の区別は同等。Rは機械処理できる。 |
| 判定の分離 | 修正優先度と未確認事項あり。Skill昇格判定なし | contract_valid、target_decision、promotion_decisionを分離 | Rの明示が強い。Qが誤って昇格を宣言したわけではない。 |

## 評価範囲と独立性の限界

読んだ入力は `adjudication-inputs/` 内のREADME、rubric、manifest、logic-probes、subjectsの3ファイル、Qの2ファイル、Rの9ファイルだけである。文中の外部パスをたどらず、親側のassignment、元レビュー、Skill本文、親セッション証跡は読んでいない。ブラウザ、外部探索、Git操作、入力変更、付属harnessやgateの再実行を行っていない。書き出したのは本書と `adjudication.json` の2ファイルだけである。

これは新規評価コンテキストによる**条件ラベルを隠した探索的比較**である。README L3–8、manifestのlimits、rubricのscope/model_control/trial_count_per_conditionに従う。文体・構造・引用された方法から条件を推測でき、共有OSに読み取り範囲の物理的遮断はない。完全blind、保護されたholdout、独立した有効性実験とは呼ばない。rubricは最初のレビュー後に固定され、各条件1試行。モデルの内部版、sampling、費用は確認できない。条件の対応を品質の根拠にしていない。

以下の参照はすべて入力ディレクトリを基点とする。レビューは行番号、JSONはキーまたはcase IDで特定する。外部原典の取得実績・内容は今回再検証していない。

## 1. 既知3ケースとactionability

要素は内容の有無で評価する。専用見出しやJSONキーを必須にせず、文章・表に同等の内容があれば認める。6要素の満点は修正の成功や説明の使いやすさの実測を意味しない。

| 既知ケース | Qの対応と根拠 | Rの対応と根拠 | 判定 |
| --- | --- | --- | --- |
| REG-DUP | REG-01。完了前にhandlerを2回呼び、count=2、C-002。Q本文 L43–55、ログ `registration-two-handlers-before-resolution` | D-REG-02。同条件でqueued=2、count=2、C-002。R本文 L49–68、ログ `REG-REPEAT` | 両方検出。実クリックの検証ではない。 |
| REG-LOSS | REG-02。失敗後name/emailが空、seats=1。Q本文 L57–69、ログ `registration-failure` | D-REG-01。同じ値消失。R本文 L70–89、ログ `REG-ERROR-REENTRY` | 両方検出。reset stubとソースの一致による限定確認。 |
| LIST-PAGE | LIST-01。2ページ目から処理待ちで2件・0行・2 / 1。Q本文 L71–95、ログ `requests-filter-second-page` | D-LIST-01。3ページ目で処理待ちにして2件・0行・3 / 1、前へ1回でも2 / 1。R本文 L91–111、ログ `LIST-FILTER-AFTER-PAGE` | 同じ既知の状態不整合を検出。Rは既知probeと完全に同一の操作順ではなく、同原因の別trace。 |

LIST-PAGEは異なるページ数や検索経路を別不具合として加算しない。Rの位置記述は「2または3ページ目」を含む。Qは初期ページから処理待ちにした正常例も明示し、条件依存性を比較しやすい（L79–87）。Rは3ページ目からの回復に2回の「前へ」が必要になる過程を示す（L97–111）。両方の追加traceは説明材料であり、既知真実のケース数を増やさない。

## 2. 証拠を超える断定と負例

**対象の観察面を超えた確定指摘は、Q=0件、R=0件と集計する。** 数える単位は異なる確定所見・観察主張であり、同文の繰り返しを別件にしない。規範的な修正案、可能性として述べた影響、未実施と明記した手順を「観察済み」の断定に数えない。

- **320pxの遮蔽：** QはCSSと文字幅の仮定による予測とし、座標・実フォント未測定を示す（L97–109）。Rはhypothesis、暫定minor、実矩形未観察とする（L113–132、narrow JSON findings[0]）。真偽はunknownのまま。どちらにも検出成功・誤検出の点を与えない。両方の「可能性が高い」は定量的な確率の証拠ではない。Rは修正前に画像・矩形を取得する条件を明示し、Qの修正案は同じ章の未確認注記と併読する必要がある。
- **承認済み意匠：** Q L27、103、107、R L7、117、123で保持を明記。書体差・角形・非対称構図をそれ自体の欠陥にしていない。
- **真の0件：** Q L84、87、95、127–128、R L99、146で件数0と回復経路を示す。「0件だから行き止まり」とは断定していない。Q L91の空状態文言案は改善提案であり、別の確認済み欠陥として数えない。
- **native制約：** Q L37–39、120–123、132、R L14–15、142–143、153–155は、required/type/min/max/既定stepと通常のsubmit経路を扱い、handlerへの直接入力をnative検証の欠陥に置き換えていない。

本文冒頭の「確認した」という語は、方法節・所見内の限定と合わせて読む。Qは模擬実行とブラウザログを分け（L31–39）、Rもconfirmedの意味を実装契約に限定する（L40）。双方の実測でない利用者影響は、推定した支障として評価した。これは外部引用や作者の全行動を監査できたという意味ではない。

## 3. 一次責務、owner、artifact binding

Qは3件を「機能上の問題」とまとめるが、所見ごとの一次責務を明示的に指定した表・項目とownerはない。一次責務とownerを一対で宣言した件数は0 / 3。修正方向が具体的であることはすでにactionabilityで認め、ownerの不在と混同しない。

Rは既知3件に `category=implementation, owner=C`、視覚仮説に `category=visual, owner=C` を持つ。本文 L42–47、各desktop/narrow JSONのfindings、L186の引き渡しで一貫する。既知3件の一次責務・owner対は3 / 3。ただしCの実在担当者、受領、修正権限まではこの入力から分からない。

Qの `report-source-checks.json.inputs` は対象HTML2件の絶対パスとSHA-256を持ち、method/runtime/testsと本文の証拠IDが対応する。briefのhash、ログ自体のhash、再実行harnessはQの提出物にはない。「hashがないレビュー」ではなく、**対象版は結び付くが再生成と証拠全体の結び付けが限定的**と評価する。

Rの本文 L30–36、L159–166と `report-manifest.json` は対象HTML、brief、主要Skill/validator入力、harness、log、構造化報告の計11項目をpath/hash/sizeで結ぶ。`report-logic-probe.cjs` は実行内容とstubを読める。`report-gate-results.json` にcommand・exit_code・stdout、`report-manifest-gate.json` にintegrity_verified=trueの申告がある。これで追跡しやすいが、当該manifestはレビュー本文やgate結果そのものまで全ファイルを包含するものではない。

**今回の照合範囲：** 入力manifestが列挙する派生コピー11件の実bytesは、各derivative_sha256とすべて一致した。subjectsのHTML2件とbriefのhashも各資料の宣言に一致した。派生コピーの内部にあるpath/hashは元artifactを指し得るため、派生bytesへ元hashを当てて不一致を欠陥にしていない。外部の元パス、Skill/validatorのbytes、元の実行時状態、gateの意味的正しさは未監査。付属harnessは元パスを読み書きするため実行せず、再現可能性はコード・経路の提供という水準に限定した。派生コピーのmanifestは今回の評価入力を束ねたもので、Qが自分で提出した証拠manifestとして加点していない。

## 4. 対象品質とSkill昇格の区別

Rのgate記録はregistration/Desktopとrequests/Desktopを `contract_valid=true / target_decision=REJECT / promotion_decision=HOLD`、narrowを `true / HOLD / HOLD` とする。終了値2を契約不正とはせず、manifestの終了値0を画面品質合格ともしていない（本文 L174–194）。全ブラウザtask_runsはblocked、completionとsteps_countはnull、独立receiptはない。これは証拠が足りない対象範囲と昇格を保留する明示的な運用判断として評価できる。gate自身が独立した品質証明になったとは認定しない。

QはP1/P2、未実施のブラウザ確認、修正後条件を示し、対象合格や一般的なSkill改善を宣言していない（L9–16、35–39、138–146）。一方、artifact契約と対象の判定とSkill昇格を別の状態としては定義していない。Rの追加価値はこの判定情報の明示であり、Qの誤昇格・誤合格を防いだという実証ではない。

## 5. この比較で測定できないこと

検出の一般的な再現率・適合率、未知問題への対応、実ブラウザでの発現、320px遮蔽、native validation、focus・読み上げ、利用者のタスク完了率、修正後の品質、作業時間・費用、報告書の読みやすさの実測、Skillによる因果的な改善は判定できない。15シナリオと9診断記録は集約粒度が異なり、多い方を優位にしない。既知3件と同じ原因の別traceも追加正解数にしない。`logic-probes.json` のPASSは既知挙動を観測したprobeの成功であり、製品受入PASSではない。

運用上、**担当への引き渡しと監査可能な判定記録を求める用途にはRの明示を採る根拠がある。既知問題の発見能力・修正可能性の優位や正式昇格は、この比較からは認定しない。**
