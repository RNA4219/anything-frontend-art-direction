# Anything Frontend — Interaction Design / UX Flow

## 最初に固定すること

1. 現行画面、要件、API、既存Skill、修正履歴を読む。既存対応を未実装と決めつけない。
2. 目的を **開始状態・目的状態・操作順序・分岐・復帰経路・完了判定** へ変換する。調査で観察した利用者行動と仮説を分ける。
3. Art Directionの視覚的意図、既存トークン、コンテンツを固定する。Bの問題を配色や装飾の好みで解決しない。
4. 機能の採否・情報構造はA、部品/ARIA/レスポンシブはC、横断的QAと正式昇格はDへ渡す。Bではタスクを完了するための振る舞いと、その証拠を作る。

## 入力

最低限 `actor / goal / current screen or entry / required inputs / observable success / service effects` を取得する。現在の状態・権限・通信条件・戻る先・中断時に失う作業・既知の失敗を確認する。

不足を全て質問待ちにしない。判断に影響しない不足は仮置きする。サーバーの冪等性、取消し可否、保存済みかどうかは仮定で保証しない。API不明時は未解決契約を残し、該当動作の完成を主張しない。

## 処理手順

### 1. タスク境界を決める — B01

journeyのどこを扱うかを示し、開始条件と利用者に見える完了の証拠を書く。「送信ボタンを押す」は通常、完了ではない。画面内で完了できないなら、外部引継ぎ先と引継ぎ済みの判定を定義する。

### 2. 状態と遷移を列挙する — B02

画面と状態を別に扱う。各遷移に `event / actor / guard / effect / feedback / preserved data` を記す。正常、入力不正、処理中、失敗、結果不明、成功、説明付き離脱のうち必要な状態を設ける。

全stateから成功または説明付き離脱へ抜ける経路を作り、entryから少なくとも1つのsuccessへ到達させる。修正ループは許す。出口のない循環、実現不能なguard、永遠の待機を放置しない。

### 3. 操作の意味を固定する — B03・B04

戻る、閉じる、未送信の破棄、処理の取消要求、確定済み変更のundoを区別する。保持する入力と失われる結果を明示する。

入力の修正、確認、送信を分ける。確認画面を全操作へ一律追加しない。可逆性、誤操作時の損失、検証で防げるかを判断する。既存native form検証とEnter送信を壊さない。

### 4. 非同期と回復を設計する — B05〜B08

- API受付、処理完了、UI表示完了を混同しない。
- 書込み結果が不明なら、照会または契約上安全な同一key再試行を選ぶ。新しいkeyで盲目的に再送しない。
- 通信のabortや画面のcloseを、server処理の取消し完了と表示しない。
- 古い応答、二重起動、取消しと完了の競合、途中離脱、部分成功をモデル化する。
- 入力不正、業務上の拒否、通信失敗、結果不明、認証切れを分け、修正・照会・再試行・再開・退出の経路を与える。
- 進捗を測れないときに架空のpercentを表示しない。待機期限後の状態と次の操作を定義する。

### 5. 手順を点検する — B09

同じ目標で通常経路と回復経路を一手ずつ辿る。各操作が必要情報の取得、意図の確認、実行、修正、終了のどれを担うか説明する。理由のない再入力、往復、二重確認を削る。クリック数が少ないことを品質の証明にしない。

### 6. 実装し、証拠を保存する — B10

[出力契約](references/flow-contract.md)に従ってFlow JSONとdecision logを出力する。checkerを実行し、guard充足性とAPI保証はレビュー・実装テストで別に確認する。

以下はSkillディレクトリを作業ディレクトリとする。

```sh
python checks/check_flow.py tests/fixtures/booking.json --json
python checks/check_flow.py tests/fixtures/report.json --json
python -m unittest discover -s tests -p 'test_*.py' -v
```

画面では正常・異常・境界の操作を実行する。ブラウザを使えない場合、node等の実行検査と未実行のUI検査を分ける。checker成功を「利用者が迷わず完了できる」「WCAG適合」と呼ばない。

通常のflow修正は対象taskの検証と未検証事項を残して提出する。2課題比較、独立評価、R-ASIはSkill効果の比較・正式昇格campaignで必要になった場合の追加条件であり、小修正のための必須依存ではない。

## 判断ルール早見表

| 入力条件 | 選ぶ処理 | 原則 |
|---|---|---|
| 複数接点・長期間の目標 | journeyを背景に置き、今回のtask境界を切る | B01 |
| 1画面に編集/送信中/拒否/確定が共存 | 画面を増やす前に状態を分ける | B02 |
| 重大な誤りを可逆性や入力検査で防げない | 確認と修正の機会を設ける | B03 |
| 閉じても処理・保存が続く | 「閉じる」と「処理を取り消す」を分ける | B04 |
| 応答が無いが書込み済みの可能性がある | unknownから照会・同一key再試行・未解決の明示へ進む | B05 |
| 一部だけが処理中 | 関連領域にfeedbackを置き、独立操作を維持する | B06 |
| エラーで有効入力が残っている | 保持して該当箇所だけ修正できる経路を示す | B07 |
| 途中離脱・部分成功・再訪がある | task ID、確定結果、失敗部分を復元・再照会する | B08 |
| 無意味な往復・二重入力がある | 各操作の目的を確認し、不要分だけ削除する | B09 |
| 自動検査のみ・自己評価のみ | 通常提出では検証範囲を限定する。Skillの正式昇格を求められた場合はその判断を保留する | B10 |

## Output contract

必須: `task contract + flow JSON + decision log + test traces + unresolved dependencies`。

指摘は `分類 / state・transition・画面位置 / 再現条件 / 観察 / 期待と根拠 / 影響 / 修正方向 / 検証状態` を持たせる。機能設計、情報構造、インタラクション、視覚設計、実装を区別する。ラベルの意味や文字量が操作に影響した場合はその影響を示す。題材や文章の好みを不具合にしない。
