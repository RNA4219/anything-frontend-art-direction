# 適用例と不適用例

通常の小修正には、対象taskの契約・実行trace・未検証事項を残す。Skill自体の効果比較を依頼されていなければ、2つ目のtask、baseline比較、R-ASI、独立評価待ちを作業開始の条件にしない。

## 例1 — 参加予約の応答を失った

入力: 名前と1〜8人の参加人数を送る。serverは同じkey・同じpayloadを一度だけ確定し、keyで結果を照会できる。回線断はcommit前後どちらでも起きる。

判断: B05を適用する。送信待ちを単なる失敗へ変えず、`unknown` にする。入力とkeyを保持し、結果を確認する。foundならreceiptを表示、pendingなら待機または退出、未処理が確定した場合だけ同じ論理操作を安全に再試行する。取消しAPIが無ければ画面を閉じる動作で予約を取り消したと表示しない。

| 状態 | 操作/応答 | 次の状態 | 保持する事実 |
|---|---|---|---|
| 編集 | 妥当な入力で送信 | 送信中 | payload、operation key |
| 送信中 | receipt受信 | 完了 | 確定ID |
| 送信中 | 応答喪失 | 結果不明 | 元のpayloadとkey |
| 結果不明 | 結果を確認 | 再照会中 | 同じkey |
| 再照会中 | 確定済み | 完了 | server receipt |
| 再照会中 | 未処理が確定 | 再試行可能 | 元の意図と入力 |

失敗例: catch節で新しいkeyを作り再送し、二重予約する。ローディングを消しただけで未予約と断定する。

実行可能な完全graphは [booking fixture](../tests/fixtures/booking.json)。fixtureは取消APIも備える別の模擬契約なので、そのserver取消分岐をAPIの無い製品へコピーしない。

## 例2 — 非同期インポートが一部失敗した

入力: a/b/cの3件を登録するjob。aとcは確定、bだけ拒否。job IDから結果を取得でき、失敗したIDだけ再実行できる。

判断: B07/B08を適用する。画面は「2件完了、1件要修正」とし、bの理由と再試行入口を出す。a/cを全体retryに含めない。refresh後はjob IDを照会し、成功したというローカル表示だけを復元しない。取消し要求中にjobが完了したら、取得した確定結果を示す。

出力: item別状態、失敗subset、jobのcancel/resume契約、部分終了と全件成功を分けたsuccess predicate。

失敗例: 最後のpromiseがrejectしたので全3件を未登録と表示する。全件再送してa/cを二重登録する。cancelボタンを押しただけで処理済みa/cも消えたように表示する。

## 例3 — 0件のレポートはエラーとは限らない

入力: 検索条件に一致する行が0件でもAPIは正常終了する。利用者の目的は対象期間のレポート結果を確認すること。

判断: B01/B06を適用し、0件の事実と条件変更の入口を示す。0件が正常結果か、データ未投入かはservice契約から決める。全てのemptyをerrorへ変えない。

実行可能なgraphは [report fixture](../tests/fixtures/report.json)。正常取得、エラー後retry、長時間待機の解除を含む。

## 不適用・過剰適用を避ける例

| 依頼/条件 | 判断 |
|---|---|
| 静的な映画祭ポスターの書体を選ぶ | Art Directionの担当。Bの状態グラフを追加しない。 |
| 2項目の即時保存設定にstepperを付けたい | 部品の存在を理由に3画面へ分割しない。可逆性・保存feedbackを確認する。 |
| 閲覧だけの一覧取得が失敗 | read retryを検討する。writeのidempotency keyを機械的に要求しない。 |
| autosave済みの編集画面を閉じる | 明示された保存方針に合わせる。変更を捨てるcancelと混同しない。 |
| ラベルの言い回しが好みでない | 操作の意味を誤認する再現事実が無ければBの不具合としない。 |
| 正常graph checkerがPASS | guardや実DOMの動作、人間の操作発見性までPASSにしない。 |

```text
原則: B05
入力: reserveはkeyを原子的に記録。lookupは確定結果を返す。API契約への参照あり。
採用: timeoutをunknownとして同じkeyを保持し、先に結果を照会する。
例外: lookup自体が失敗したら確定/未確定を断定しない。
根拠: S12。UIへの移植は本Skillの推論。
検証: commit済み応答喪失を注入し、receipt回復とserver確定数1を確認する。
未検証: 実利用者のラベル理解、対象サービスでのkey保持期限。
```
