# レビュー依頼テンプレート

[入口](../SKILL.md) · [評価プロトコル](../references/evaluation-protocol.md)

## 単独のDesign QA

次のブロックの角括弧を実入力で置き換える。秘密情報や非公開の評価oracleを公開検索へ送らない。

```text
anything-frontend-design-qaを使って、[artifact/path/版]を評価してください。
利用者は[利用者条件]で、[開始状態]から[目的状態]に到達したいです。
要件は[要求ファイル]、実内容は[入力ファイル]です。
既存のArt Directionの意図は[意図/維持する表現]です。
対象環境は[viewport/browser/入力方式]です。
正常系、想定する失敗、境界条件を確認してください。
所見は位置・症状・根拠・影響・修正方向・再現手順と証拠を示してください。
画面の実装を変更せず、未検証事項と他担当への引渡しを分けてください。
出力は[report保存先]とし、対象UIの判断とSkill昇格の判断を区別してください。
```

## baseline/candidate比較

課題本体は両条件で同じbytesを使う。既存Art DirectionだけのbaselineにD契約や候補の正解例を渡さない。条件ごとに追加する読み込み指示だけを変える。

**共通の課題本体:**

```text
[artifact/path/版]のUIをレビューしてください。
目的・要件・実内容・利用者条件は[同一のtask brief]を参照してください。
利用可能な[同一ツール/環境]で画面と操作を確認してください。
問題があれば、どこで何が起き、利用者の目的にどう影響するか、根拠と再現手順を示してください。
実装は変更せず、確認できた結果と確認できなかった事項を報告してください。
出力先は[この試行の固有path]です。
```

| 条件 | 読み込み指示 |
| --- | --- |
| baseline | 固定した版の既存Art DirectionのSKILL.mdを使い、必要な既存references/checklistsを参照する。 |
| candidate | 同じ既存Art Directionに加え、固定した版のextensions/D/SKILL.mdを使う。 |

出力先の相違は実行管理上必要な差として記録する。それ以外の課題・モデル・ツール・予算を可能な限り合わせる。baselineが自由文でも、意味のある所見は同じrubricで扱う。D形式の有無だけを所見の正しさとして採点しない。

## 評価者への依頼

```text
匿名ID [X] と [Y] の二つのレビューを、生artifact・要求・実操作証拠と照合してください。
各所見を支持/反証/判定不能に分け、対応する根拠と位置を示してください。
重複は対応付け、所見の具体性、正常/異常/境界の確認範囲、証拠への追跡を比較してください。
作者名、使用Skill、どちらが候補かは提示しません。
比較対象の出力を書き換えず、採点結果と不一致を独立したファイルに保存してください。
確認できないことを好意的に補完しないでください。
```

これは評価者へ期待解を教えるテンプレートではない。別のoracleがある場合は評価者だけがアクセスできる隔離環境で管理する。共有ファイル環境で単に閲覧しないよう頼んだ場合、文脈分離の比較として記録し、protected blindの正式昇格を主張しない。

## 最終報告の並び

1. Completed: 確認した対象と能力、今回変更した評価契約。
2. Evidence: 実行ケース、所見と証拠、比較条件、対象hash、receipt、試行履歴。
3. Open: 未確認・環境不足・未解決所見・独立性の不足・他担当への引渡し。
4. Decision: READY FOR INTEGRATION / HOLD / REJECT。何に対する判断かを明記する。

対象UIがREJECTでも、欠陥を正しく発見したレビュー自体は有用になり得る。Skillの形式検査・レビューの有用性・対象UIの品質・正式昇格を一つのPASSへまとめない。
